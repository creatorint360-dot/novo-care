Overview

What was built

Novo Care is a login and record system for clinic staff. Nurses, doctors, records officers and administrators each see only what their role allows. The same code can model a school, a bank or a staff office by changing one setting.

Live online

Website

Hosted on Render at novo-staff.onrender.com. It installs on a phone home screen as a web app.

Real database

PostgreSQL on AWS

An Amazon RDS database in Stockholm (eu-north-1), reached over verified TLS.

Mobile

Android app

An Expo (React Native) app that signs in to the same server and shows the same features.

Security

Layered protection

Salt, pepper, slow hashing, 2FA, lockout, encryption, audit log and server-side permissions.

Architecture

How the pieces connect

The browser and the app both talk to one server. Only the server can reach the database, and it connects as a limited database user.

Server

Plain Node.js http server. Each feature is one file in api/; shared security code sits in lib/.

Database access

The server uses the novostaff_app account. It can read and write only the tables it needs. It cannot drop tables or change the schema.

Firewall

The AWS security group accepts database connections only from Render's address ranges and from approved admin addresses.

Secrets

Pepper, encryption key and signing key live in Render environment variables, never in GitHub.

Core requirement

Salt and pepper, step by step

A password is never stored. What is stored is a slow, one-way hash that was made from the password, a random salt and a secret pepper.

Make a salt16 random bytes, shown as 32 hex characters, made fresh for every user. Two people with the same password still get different hashes.
Add the pepperOne secret value shared by the whole system, read from the PEPPER environment variable. It is not in the database, so a stolen database alone cannot be attacked.
Join themsalt_pepper = salt + pepper. This joined value is the salt given to the hash function.
Hash slowlyPBKDF2 with HMAC-SHA256 and 600,000 rounds. Each guess costs an attacker real time.
Compare safelyAt sign-in the same steps run on the typed password and the result is compared in constant time with the stored hash.
salt          = randomBytes(16).toString('hex')
salt_pepper   = salt + PEPPER
password_hash = PBKDF2-HMAC-SHA256(password, salt_pepper, 600000 rounds)
Why the code reads the pepper from the environment. A pepper written in the source would be public on GitHub and protect nothing. The recipe is visible in lib/security.js; the secret value is not.

Sign-in

Protection around the login

2FA

Authenticator codes

Time-based one-time passwords (RFC 6238). Works with Google Authenticator and similar apps. The secret is stored encrypted.

Lockout

Five tries

Five wrong passwords lock the account for 15 minutes. This slows down guessing.

Sessions

Signed cookies

Sessions are signed with HMAC and can be cancelled instantly with a session version number, for example after a password change.

CSRF

Request header check

Every change request must carry a custom header that other websites cannot add.

Encryption

AES-256-GCM

Patient notes and 2FA secrets are encrypted before they reach the database.

Audit

Activity log

Sign-ins, failures, changes, backups and restores are recorded with who and when.

Added after lecturer feedback

Backup, restore and reset

Backup

One button

Copies all users and notes into an encrypted snapshot in the database. The newest 20 are kept.

Restore

Go back to a snapshot

Administrator only. Asks for the password again. A safety backup is taken first, then the notes return to that snapshot.

Reset

Clear the notes

Administrator only. Needs the password and the typed word RESET. It empties the notes after a safety backup.

Reset does not change settings. Accounts, passwords, 2FA, roles and system settings are never touched by restore or reset. Only the stored notes change, and every use is written to the audit log.
